# PROE Reforged – Vision & Entscheidungsgrundlage

> „PROE Reforged“ war der Arbeitstitel. Das Spiel heißt heute **AETHON – The E3 Initiative** und ist eine geistige Nachfolge von *Perry Rhodan: Operation Eastside* (siehe [Namenskonzept](26%2005%2002%20Namenskonzept.md), [Kernspielidee](26%2005%2002%20Kernspielidee.md)).

## Ausgangspunkt / Motivation

Ich möchte das Spiel *Perry Rhodan: Operation Eastside* in irgendeiner Form wieder spielbar machen bzw. weiterentwickeln.

Ursprüngliche Idee:
- vollständiger Nachbau (Remake)
- inklusive Assets und Spielmechaniken

Probleme:
- Rechte an Code und Assets unklar / fragmentiert
- Zugriff auf Original-Quellcode nicht möglich
- Multiplayer-Bug im Original nicht gefixt

---

## Erkenntnisphase (Brainstorming-Ergebnisse)

### 1. Zwei grundsätzliche Wege

#### Weg A – Spiritueller Nachfolger
- eigene Implementierung
- eigene Assets
- gleiche Spielmechaniken / Spielgefühl
- inspiriert vom Original

#### Weg B – Fan-Patch / Reverse Engineering
- Originalspiel behalten
- Bugs patchen (Binary / Hooking)
- minimale Features ergänzen

---

### 2. Bewertung der Wege

#### Weg A – Vorteile
- keine Rechteprobleme
- volle Kontrolle über Features
- langfristig erweiterbar
- veröffentlichbar (Web, öffentlich zugänglich)

#### Weg A – Nachteile
- hoher initialer Aufwand
- viele Designentscheidungen notwendig

---

#### Weg B – Vorteile
- schneller Einstieg
- vorhandenes Spiel bleibt erhalten
- weniger Entwicklungsaufwand

#### Weg B – Nachteile
- technisch komplex (Reverse Engineering)
- schwer wartbar
- begrenzte Erweiterbarkeit
- Multiplayer-Bug evtl. schwer lösbar

---

### 3. Zentrale Erkenntnis

Der wichtigste Teil ist nicht das Coding, sondern:

- Systemdesign
- Regeldefinition (Operationalisierung)
- Datenmodellierung

→ ca. 70–80 % der Arbeit

---

## Strategische Neuausrichtung

Inspiration durch:
- **Widelands** (spiritueller Nachfolger von Siedler 2)

Prinzip:
- Mechaniken übernehmen
- Umsetzung komplett neu
- eigene Assets + eigene IP

---

## Rechtliche Leitplanken

Erlaubt:
- Spielmechaniken übernehmen
- ähnliche Spielstile (z. B. „Schwarm-Rasse“)

Nicht verwenden:
- originale Assets (Grafiken, Sounds)
- originale Namen (z. B. Fraktionen)
- originale Story/Lore

Faustregel:
> „fühlt sich gleich an“ ist ok  
> „ist erkennbar das gleiche“ ist zu nah

---

## Technische Vision

### Architektur

- Spielmodus heute: Singleplayer im Browser, Spielstand im `localStorage`, kein Backend nötig
- Backend (für späteren Multiplayer): TypeScript/Bun mit Hono, Drizzle, PostgreSQL, Hosting noch offen (bis 29.05.2026 C#/.NET mit ASP.NET Core und Entity Framework auf Railway, dann portiert). Details: [SW-Architektur](26%2005%2002%20SW-Architektur.md)
- Frontend: Web (React + TypeScript), ausgeliefert über Cloudflare Pages
- Rendering: 2D (Canvas/WebGL) – konkret: PixiJS (isometrisch)

Vorteile:
- sofort spielbar im Browser
- kein Installationsaufwand
- leicht teilbar

## Erstes konkretes Projektziel

### Vertikaler Prototyp: Planetensimulation

#### Scope (bewusst klein)

- 1 Planet
- Grid / Felder
- wenige Gebäudetypen:
  - Produktion
  - Energie
  - Konsumgüter
  - schwere Industrie
  - Wohnraum

- 1 Tech-Level
- keine Flotten
- kein Multiplayer
- keine Fraktionen

---

### Funktionale Anforderungen

- Gebäude platzierbar
- Tick-System (z. B. Button oder Timer)
- Ressourcen ändern sich sichtbar
- einfache UI (Zahlen reichen)

---

### Ziel

> „Ein spielbarer Kernloop auf einem Planeten“

Wenn erreicht:
- echtes Spielgefühl testbar
- Basis für Erweiterung

## Langfristige Perspektive

Das Spiel hat zwei Ebenen: die **Planetenebene** (Ressourcen erzeugen, Planeten besiedeln und ausbauen), an der aktuell gearbeitet wird, und später die **Raumebene** mit Militär.

Mögliche Erweiterungen:
- mehrere Planeten
- Fraktionen (spirituell ähnlich)
- Forschung / Tech-Level (inzwischen umgesetzt)
- Militär: Raumschiffe/Flotten, Raumkampf, Angriffe auf Planeten aus dem Orbit
- Effizienz bzw. Drosselung: Produktion abhängig von Versorgung/Unterhalt (bewusst aus der Energie-Erweiterung herausgeschoben)
- Multiplayer

Aber:
→ alles optional nach funktionierendem Kern

## Realisierungsstand V1 (abgeschlossen)

Der vertikale Planet-Prototyp ist implementiert:

- 1 Planet, 10×10 Grid, 4 Gebäudetypen (Base, Housing, Consumer, Industry)
- Rundenbasierte deterministische Simulation
- Vollständiges Backend (damals C#/.NET, PostgreSQL, Railway; inzwischen nach TypeScript portiert)
- Isometrisches Frontend mit PixiJS (Zoom, Pan, Rotation, Touch-Support)

Seitdem erweitert um Energie, Forschung (4 Zweige, Stufen T1–T5) und 20×20 Grid. Aktueller Regelstand: [Spielregeln Ist-Stand](26%2011%2022%20Spielregeln%20Ist-Stand.md)

## Historie

### Experiment: Originalspiel per Einzeiler nachbauen (29.06.2026)

Am 29.06.2026 bekam Claude als Versuch einen Einzeiler-Prompt, das Originalspiel *Perry Rhodan: Operation Eastside* nachzubauen.

Das Ergebnis war ernüchternd: ein mehr oder weniger textbasiertes Interface, das die Spiellogik grob abbildete (Galaxie, Fraktionen, Kolonien, Flotten, Kampf, Forschung), aber null UI, keinen Game Loop und kein Spielgefühl hatte. Der Ansatz wurde nicht weiterverfolgt, der Code wurde verworfen.
